# 05. AI 콘텐츠 파이프라인 설계

핵심 주장: 생성이 아니라 **보증**. 모든 출고 콘텐츠는 검증을 통과한 것만.
실패 데이터(반려율·사유)를 숨기지 않고 제시하는 것이 검증기가 진짜라는 증거다.

## 하드 파이프라인 — 스테이지
```
[1] 생성   LLM 또는 절차적 생성기가 스테이지 JSON 산출
           (지형, 배치 가능 타일, 웨이브 테이블, 성벽 HP, 코스트 파라미터)
[2] 정적검증  스키마 유효성, 경로 존재성(진입로→성벽 경로 연결), 배치 타일 최소 수
[3] 봇 시뮬  Random / Greedy / Planner 봇이 각 N회 플레이 (시드 변화)
[4] 지표    클리어율(봇 등급별), 성벽 잔여 HP 분포, 클리어 시점 코스트 여유,
           사용 유닛 다양성(특정 유닛 없으면 불가능한지)
[5] 판정    목표 난이도 밴드와 대조 → 출고 or 반려(사유 코드 부여)
           반려 사유 예: UNSOLVABLE(전 봇 실패) / TRIVIAL(Random도 클리어)
           / OFF_CURVE(난이도 곡선 이탈) / DEGENERATE(단일 전략 강제)
[6] 출고    통과분 JSON을 리포에 커밋 → 자동 배포 → 게임에 스테이지 추가
```
- 모든 실행 결과는 `pipeline/reports/`에 축적. 기술 문서의 근거 자료.
- 난이도 지표의 세부 임계값은 [미결] — W2에서 실측 데이터 보고 사용자와 확정.

## 소프트 파이프라인 — 캐릭터
```
[1] 기획 생성   세계관 문서 기반으로 프로필·스킬셋·대사 생성
[2] 정합성 검증  기존 캐릭터와 톤·설정 충돌 체크 (검증 에이전트)
[3] 밸런스 검증  스킬 수치를 시뮬에 투입, 기존 로스터 대비 기여도 측정
              (동일 스테이지 셋에서 교체 투입 → 클리어율 변화)
[4] 아트 생성   스타일 레퍼런스 고정 → 일러스트 생성 → 일관성 확인
[5] 사람 승인   최종 게이트는 디렉터(사람)
```
- 하드와 달리 **의도적으로 human-in-the-loop**: 수학적으로 검증 불가능한 콘텐츠는 사람이 게이트키퍼라는 설계 판단 자체가 기술 문서의 논지.

## 디펜스 검증 봇 = 오펜스 에이전트
- 디펜스 스테이지를 "공격해보며" 검증하는 봇의 정책은, 오펜스 모드의 자동 전투 로직과 동일한 문제.
- 오펜스 모드가 구현되면: 봇과 플레이어가 문자 그대로 같은 게임을 한다 → "검증의 신뢰성"을 게임 모드로 증명하는 구조.

## 기술 문서(제출물 4)에 담을 것
- 에이전트 구성도: 생성/정적검증/시뮬/판정/기획/정합성/밸런스 각 에이전트의 역할·입출력
- 주요 프롬프트와 지시사항 (디렉팅 로그에서 발췌)
- 반려율 통계와 대표 반려 사례 (Before/After)
- 난이도 곡선 차트: 스테이지 번호 vs 봇 클리어율
- 외부 에셋/오픈소스 출처 (asset-licenses.md)
- 48시간 본선 재현 계획: 이 파이프라인이 새 주제에 어떻게 재적용되는가
