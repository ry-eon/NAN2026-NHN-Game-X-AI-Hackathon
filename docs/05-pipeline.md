# 05. AI 콘텐츠 파이프라인 설계

핵심 주장: 생성이 아니라 **보증**. 모든 출고 콘텐츠는 검증을 통과한 것만.
실패 데이터(반려율·사유)를 숨기지 않고 제시하는 것이 검증기가 진짜라는 증거다.

## 하드 파이프라인 — 스테이지
```
[1] 생성   LLM 또는 절차적 생성기가 스테이지 JSON 산출
           (지형, 배치 가능 타일, 웨이브 테이블, 성벽 HP, 코스트 파라미터)
[2] 정적검증  스키마 유효성, 경로 존재성(진입로→성벽 경로 연결), 배치 타일 최소 수
[3] 봇 시뮬  Random / Greedy / Planner 봇이 각 N회 플레이 (시드 변화)
[4] 지표    클리어율(봇 등급별), 성벽 잔여 HP 분포, 클리어 시점 코스트 여유,
           사용 유닛 다양성(특정 유닛 없으면 불가능한지)
[5] 판정    목표 난이도 밴드와 대조 → 출고 or 반려(사유 코드 부여)
           반려 사유 예: UNSOLVABLE(전 봇 실패) / TRIVIAL(Random도 클리어)
           / OFF_CURVE(난이도 곡선 이탈) / DEGENERATE(단일 전략 강제)
[6] 출고    통과분 JSON을 리포에 커밋 → 자동 배포 → 게임에 스테이지 추가
```
- 모든 실행 결과는 `pipeline/reports/`에 축적. 기술 문서의 근거 자료.
- 난이도 지표의 세부 임계값은 [미결] — W2에서 실측 데이터 보고 사용자와 확정.

## 구현 현황 (2026-07-20, 하드 파이프라인 골격 완성)

`pnpm pipeline [--count 8] [--seed 123] [--tier HARD] [--dry]` 한 번으로 [1]~[6] 전체가 돈다.

| 단계 | 구현 | 비고 |
|---|---|---|
| [1] 생성 | `pipeline/src/generate.ts` | 절차적(템플릿+시드 변형). LLM 생성은 같은 StageDef 스키마로 교체/병행 예정 |
| [2] 정적검증 | `pipeline/src/judge.ts` `validateStage` | 스키마·경로 인접성(core `createContext`) + 스폰 수·경로 길이·종점 원거리 커버 |
| [3] 봇 시뮬 | `bots/src/evaluate.ts` `evaluateBots` | Planner/Greedy/Random × 5회 (Random만 시드 변주, 상위 봇은 결정론) |
| [4] 지표 | `BotAggregate` | 클리어율, 평균 성벽 잔여율, 평균 클리어 시간, 사용 유닛 다양성 |
| [5] 판정 | `pipeline/src/judge.ts` `judge` | 아래 CRITERIA_V0. 반려 사유 코드 부여 |
| [6] 출고 | `pipeline/src/ship.ts` | `pipeline/accepted/*.json`(진실 원천) → `core/.../generated.ts` 코드젠 → STAGES 자동 포함 |
| 리포트 | `pipeline/src/report.ts` | 실행마다 `pipeline/reports/<시각>-seed<N>.{json,md}`. 대표 1런의 액션 로그 포함(리플레이 재현용) |

### 판정 기준 v0 — CRITERIA_V0 [초안, 논의 필요]
| 규칙 | 값 | 근거 |
|---|---|---|
| UNSOLVABLE | Planner 클리어율 < 100% | Planner가 풀이 가능성의 오라클 (결정론이라 5회 전승/전패) |
| TRIVIAL | Random 클리어율 ≥ 50% | stage-001 실측(Random 100%)을 하급 신호로 채택 |
| DEGENERATE | Planner 사용 유닛 < 2종 | 단일 유닛 강제 스테이지 배제 |
| 티어 EASY | Greedy 클리어 100% & 성벽 잔여 ≥ 70% | |
| 티어 NORMAL | Greedy 클리어 100% & 잔여 < 70% | |
| 티어 HARD | Greedy 클리어 < 100% (Planner 전용) | |
| OFF_CURVE | `--tier` 목표와 불일치 시 반려 | 난이도 커브 채우기용 |

### 첫 실측 (시드 100~111, 12후보)
- 출고 8 / 반려 4 (TRIVIAL 3, UNSOLVABLE 1) — 수율 67%
- 반려 사례가 자연 발생: 반려율·사유 통계가 "검증기가 진짜"라는 증거로 축적됨
- **논의 안건**: ① 출고분이 전부 EASY — NORMAL/HARD가 나오도록 생성기 압박 상향 또는
  티어 경계(70%) 조정 필요 ② TRIVIAL 경계 50%가 적정한가 ③ 봇별 5회가 충분한가
  (상위 봇은 결정론이라 사실상 1회 — Random만 N회의 의미가 있음)

## 소프트 파이프라인 — 캐릭터
```
[1] 기획 생성   세계관 문서 기반으로 프로필·스킬셋·대사 생성
[2] 정합성 검증  기존 캐릭터와 톤·설정 충돌 체크 (검증 에이전트)
[3] 밸런스 검증  스킬 수치를 시뮬에 투입, 기존 로스터 대비 기여도 측정
              (동일 스테이지 셋에서 교체 투입 → 클리어율 변화)
[4] 아트 생성   스타일 레퍼런스 고정 → 일러스트 생성 → 일관성 확인
[5] 사람 승인   최종 게이트는 디렉터(사람)
```
- 하드와 달리 **의도적으로 human-in-the-loop**: 수학적으로 검증 불가능한 콘텐츠는 사람이 게이트키퍼라는 설계 판단 자체가 기술 문서의 논지.

### 구현 현황 (2026-07-20, [1][3][5] 골격 가동)
`pnpm pipeline:chars [--count 30] [--seed N] [--dry]`

| 단계 | 구현 | 비고 |
|---|---|---|
| [1] 생성 | `pipeline/src/char-generate.ts` | 역할 원형(봇 운용 가능 4종) × 스탯 변주 ±8% × 기술 12종 라이브러리 조합 × 생존 톤 이름/이명/서사/대사 (조합 풀 [초안], LLM 교체 가능) |
| [3] 밸런스 | `pipeline/src/char-judge.ts` | 시작 3인(Lv5) 기준 로스터에 교체 투입 → EASY/분리/HARD 3스테이지 봇 시뮬. **HARD 포함이 핵심** — 기준선 천장이 있어야 OP 판정 작동 |
| [5] 승인 | 리포트 + 커밋 | 출고분 반입 커밋 = 사람 승인. 리포트: `pipeline/reports/*-chars-*.md` |
| [2] 정합성 | 부분 (기계적) | 중복 이름·중복 기술조합 = NO_IDENTITY. 톤 충돌 검증(LLM)은 후속 |
| [4] 아트 | 미착수 | W3 아트 주간 |

- 반려 코드: **USELESS**(교체 시 Planner가 기준선이 깨던 스테이지 실패) /
  **OP**(Greedy 성벽 잔여율 평균 +20%p 초과 상승) / **NO_IDENTITY**(중복 이름·조합)
- 첫 실측 (시드 7000, 30명): 출고 23 / 반려 7 (USELESS 4 — 약한 술사가 원거리
  자리를 대체하면 HARD 실패, NO_IDENTITY 3). 영입 풀 23명 확보 (목표 20+ 충족).
- 출고 구조: `pipeline/characters/*.json`(진실 원천) → `characters-generated.ts`
  코드젠 → `CHARACTER_POOL` (영입 루프가 소비 — 3단계).

## 디펜스 검증 봇 = 오펜스 에이전트
- 디펜스 스테이지를 "공격해보며" 검증하는 봇의 정책은, 오펜스 모드의 자동 전투 로직과 동일한 문제.
- 오펜스 모드가 구현되면: 봇과 플레이어가 문자 그대로 같은 게임을 한다 → "검증의 신뢰성"을 게임 모드로 증명하는 구조.

## 기술 문서(제출물 4)에 담을 것
- 에이전트 구성도: 생성/정적검증/시뮬/판정/기획/정합성/밸런스 각 에이전트의 역할·입출력
- 주요 프롬프트와 지시사항 (디렉팅 로그에서 발췌)
- 반려율 통계와 대표 반려 사례 (Before/After)
- 난이도 곡선 차트: 스테이지 번호 vs 봇 클리어율
- 외부 에셋/오픈소스 출처 (asset-licenses.md)
- 48시간 본선 재현 계획: 이 파이프라인이 새 주제에 어떻게 재적용되는가
