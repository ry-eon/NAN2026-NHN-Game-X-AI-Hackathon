# 11. 본선 플레이북 — 대회 현장에서 다시 쓸 것들

> 사전과제(v5 「최후의 벽, 최후의 사람」)에서 **실제로 통한 방법만** 추린 문서.
> 작성 2026-08-09.
>
> ## ⚠️ 스택은 여기서 정하지 않는다
> 본선은 언어·엔진·배포 방식에 제한이 걸릴 수 있다. 그래서 이 문서는
> **TypeScript도, Three.js도, GitHub Pages도 전제하지 않는다.**
> 여기 적힌 것은 전부 "어떤 스택에서도 첫날에 세울 수 있는 구조와 절차"다.
> 스택은 §6의 판단 기준으로 **현장에서** 고른다.

## 1. 가져갈 핵심 — "생성이 아니라 보증"

사전과제에서 심사에 걸린 유일한 차별점은 그래픽도 분량도 아니었다.
**만든 것이 게임으로 성립함을 기계가 증명한다**는 구조였다. 이건 스택과 무관하다.

구조는 세 조각뿐이다:

| 조각 | 요건 | 왜 |
|---|---|---|
| **결정론 코어** | 게임 규칙 전부를 순수 함수로. 렌더·입출력 의존 0, 시드 고정 RNG만 | 같은 (시드, 입력)이면 항상 같은 결과 → 재현 가능한 검증이 성립 |
| **커맨드형 입력** | 플레이어 입력을 값(구조체)으로. 봇도 **같은 타입**만 낸다 | 뒷문이 없어야 "봇이 검증한 판 = 사람이 하는 판"이 참이 된다 |
| **판정 기준** | 통과/반려를 **코드로** 박아둔다 | 기준이 곧 게임 설계 주장이다. 말이 아니라 판정이 남는다 |

이 셋이 서면 나머지는 따라온다 — 리플레이(커맨드 시퀀스가 곧 리플레이), 밸런스 스윕,
회귀 방지, 그리고 제출용 기술 문서의 원재료.

**반드시 지킬 한 줄:** 봇 전용 API를 만들지 마라. 봇이 게임을 이기는 방법이
사람과 달라지는 순간, 검증은 시늉이 된다.

## 2. 킥오프 90분 체크리스트 (스택 무관)

대회 시작 직후, 게임 내용을 정하기 **전에** 이 뼈대부터 세운다.

- [ ] **코어/표현 분리** — 규칙 파일과 그리기 파일을 물리적으로 나눈다. 코어는 화면을 모른다
- [ ] **고정 틱** — 초당 N틱(20~30 권장) 고정. 렌더 프레임과 분리하고 보간으로 그린다
- [ ] **시드 RNG 하나** — 언어 기본 난수 **직접 호출 금지**. 코어 안에 시드 RNG를 두고 그것만 쓴다
- [ ] **입력 = 값** — `{이동:…, 조준:…, 스킬:…}` 형태의 구조체 하나로 통일
- [ ] **한 판 돌리는 함수** — `(시드, 정책) → 결과 + 커맨드 기록`. 화면 없이 돈다
- [ ] **리플레이 확인** — 기록한 커맨드를 다시 넣으면 같은 결과인지 단언하는 테스트
- [ ] **판정 기준 파일** — 아직 게임이 없어도 빈 기준을 만들어 둔다. 나중에 채운다
- [ ] **로그 파일** — `logs/YYYY-MM-DD.md`. 지시·반려·판단을 그때그때 적는다

여기까지가 90분. 이걸 안 하고 게임부터 만들면, 뒤에서 "재현이 안 돼서 못 고치는" 상태가 온다.

## 3. AI 협업 — 통한 것과 안 통한 것

사전과제 2주에서 실증된 것만.

### 통한 것

- **레퍼런스를 스펙으로 재유도한다.** "스타크래프트처럼"으로는 기존 구현에 억지로 갖다 붙인다.
  레퍼런스의 **조직 원리**를 먼저 말로 뽑아낸 뒤(예: "카드 = 현재 선택이 할 수 있는 일")
  그걸 스펙 삼아 다시 만들게 해야 바뀐다.
- **"이유부터 찾아라"** — 증상만 말하면 표면을 계속 고친다. 실제로 사전과제에서 같은 표시
  버그를 **다섯 번** 고치고서야 원인(높이를 무시하는 판정 = 원기둥을 2D로 그리려는 시도)에
  도달했다. "고치지 말고 원인부터"라는 한 마디가 그 반복을 끊었다.
- **숫자로 답하게 한다.** "이게 맞나?"보다 "재서 보여줘"가 빠르다. 실측 한 번이
  추측 다섯 번보다 싸다.
- **확정 사항을 문서에 박아둔다.** 세션이 바뀌면 옛 방향으로 되돌아가려 한다.
  "재론 금지" 표를 만들어 두면 그게 막힌다.
- **반려 이유를 남긴다.** 왜 물렸는지가 다음 판단의 근거가 되고, 그대로 제출 문서 재료가 된다.

### 안 통한 것

- "예쁘게 해줘" 류의 형용사 — 판정 불가라 매번 다른 결과가 나온다
- 이전 확정을 근거로 새 의견을 막는 것 — 전제가 바뀌면 수치도 다시 재야 한다.
  실제로 "사거리를 줄이자"는 옳은 판단이 **서는 위치가 바뀐 뒤에는 틀린 값**이 됐다
- 한 번에 여러 곳 수정 — 판정이 움직였을 때 원인을 못 가른다

## 4. 반복해서 밟은 함정 (일반화)

스택이 달라도 형태는 같다. 미리 알고 가면 시간을 크게 아낀다.

| 함정 | 증상 | 원인의 형태 |
|---|---|---|
| **자동화 탭은 안 그려진다** | 성능·연출 측정값이 전부 0, 게임이 안 흐름 | 브라우저/엔진이 비활성 창의 프레임 루프를 멈춘다. **사람 눈으로 볼 창에서만** 측정 |
| **판정과 표시의 차원이 다름** | "범위 표시가 실제와 다르다"가 반복됨 | 판정은 2D인데 화면은 3D. 어느 단면을 그릴지 정하지 않으면 매번 다른 데서 깨진다 |
| **일방적 사거리** | 아군이 맞기만 하고 반격 못 함 | 적의 접근 정지 거리 > 아군 공격 거리. **몸통 반경을 넣고 재야** 대칭이 맞는다 |
| **최근접 우선 조준** | 보스가 늘 마지막에 죽음 = 보스전이 없음 | 자동 조준이 거리순이면 중요한 표적을 영원히 안 친다 |
| **경계에서 끼는 유닛** | 특정 지형 경계에서 영구 정지 | 축별 슬라이드가 서로 상쇄. 지점을 막지 말고 **정체 감지 → 재경로 → 포기** 규칙으로 |
| **전제가 바뀐 수치** | 어제 옳던 밸런스가 오늘 틀림 | 측정의 전제(유닛이 서는 위치 등)가 바뀌면 그 위 수치는 전부 무효 |
| **표시 없는 상태** | 플레이어가 규칙의 존재를 모름 | 준비 단계엔 전투가 없어 피드백이 0. 상태마다 **보이는 신호**를 따로 만들어야 한다 |

## 5. 시간 배분 (개인 기준, 팀이면 축을 나눈다)

사전과제 실적 기준 역산.

| 구간 | 비중 | 내용 |
|---|---|---|
| 뼈대 | 10% | §2 체크리스트. 여기서 아끼면 뒤에서 배로 낸다 |
| 규칙 | 30% | 게임 규칙 + 판정 기준 채우기. **화면 없이** 돌려보며 |
| 표현 | 30% | 렌더·연출·UI. 규칙이 서고 나서 |
| 검증·조정 | 20% | 스윕으로 수치 잡기. 여기서 반려 이력이 문서 재료가 된다 |
| 제출물 | 10% | 영상·문서·링크. **마지막 날에 몰면 반드시 터진다** |

팀이라면 축을 이렇게 나눈다: **규칙(코어) / 표현(렌더) / 검증(봇·스윕)**.
셋이 같은 입력 타입만 공유하면 서로를 안 막는다.

## 6. 스택은 현장에서 — 고를 때의 판단 기준

미리 정하지 않는다. 대신 아래 순서로 **현장 제약에 맞춰** 30분 안에 고른다.

1. **주최 제한 확인이 먼저다** — 허용 언어·엔진·라이브러리·런타임 비용·배포 방식.
   여기서 걸리면 나머지 판단이 전부 무효다
2. **결정론이 가능한가** — 시드 RNG를 통제할 수 있고, 물리/부동소수 결과가 재현되는가.
   재현이 안 되는 엔진이면 §1이 성립하지 않으니 **규칙만이라도 엔진 밖에** 둔다
3. **화면 없이 돌릴 수 있는가** — 헤드리스로 한 판을 빨리 돌릴 수 있어야 스윕이 가능하다
4. **심사자가 여는 비용** — 설치 없이 열리는 쪽이 유리하다. 다만 배포 방식이 제한될 수 있으니
   **빌드 산출물을 정적으로 서빙하는 형태**를 기본으로 두고, 실제 호스팅은 현장 지침을 따른다
5. **런타임 유료 의존 금지** — 요건에 자주 등장한다. AI 생성물은 **빌드 타임에** 굽는다

> 사전과제에서 쓴 조합은 참고일 뿐이며 본선에서 그대로 간다는 뜻이 아니다.
> 옮겨야 하는 건 스택이 아니라 §1의 세 조각이다.

## 7. 산출물 템플릿 (그대로 재사용)

- **디렉팅 로그** `logs/YYYY-MM-DD.md` — 지시 원문 요지 · 반려 사유 · 그래서 무엇을 바꿨나 ·
  측정값. 하루 끝에 몰아 쓰지 말고 그때그때. 제출용 기술 문서가 이걸로 만들어진다
- **판정 리포트** — 시드 × 정책 표 + 통과/반려 + **반려 사유 전문**.
  통과만 남기면 아무 설득력이 없다. **실패가 남아야 검증이 진짜였음이 보인다**
- **확정 사항 표** — 항목 / 결정 / 날짜. 재론 금지 목록
- **잔여 작업** — 우선순위와 폴백 순서. "시간이 모자라면 무엇부터 버리는가"를 미리 적어둔다

## 8. 첫 30분에 물어볼 것 (현장 체크리스트)

- 제출물 목록과 형식 — 영상 길이·문서 종류·링크 형태
- 기술 제한 — 언어/엔진/라이브러리/유료 API/에셋 라이선스
- 심사 기준의 가중치 — 완성도인가 독창성인가 기술성인가
- 배포·실행 방식 — 링크인가 로컬 실행인가, 환경은 무엇인가
- 커밋/기록 요건 — 히스토리를 보는가, 중간 산출물을 요구하는가

답에 따라 §6의 선택이 달라지고, §5의 비중이 달라진다. **이걸 먼저 묻는 게 첫 수다.**
