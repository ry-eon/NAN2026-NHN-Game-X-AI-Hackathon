# 03. 아키텍처

## 설계의 존재 이유
"봇이 검증한 스테이지 = 플레이어가 플레이하는 스테이지"라는 보증이 프로젝트의 핵심 주장이다.
이 보증은 **게임과 검증기가 문자 그대로 같은 코드를 실행할 때만** 성립한다. 따라서:

```
core/      순수 TypeScript 시뮬레이션 (단일 진실 원천)
client/    Phaser 3 렌더러 — core의 상태를 그리기만 함
bots/      core를 헤드리스로 구동하는 플레이 에이전트
pipeline/  생성 → 검증 → 출고 스크립트 (Node)
docs/      기획·로그·라이선스
```

## core/ 규칙
- 의존성 0에 가깝게. Phaser, DOM, window 참조 금지. Node/브라우저 양쪽에서 동일 동작해야 함.
- **고정 틱 시뮬레이션**: `step(state, inputs) -> state`. 프레임레이트와 무관한 결정론.
- **시드 RNG**: 모든 무작위성은 주입된 시드 RNG 경유. `Math.random()` 금지. (같은 시드+같은 입력 = 같은 결과 → 봇 검증 재현성, 리플레이 가능성)
- 스테이지는 JSON 스키마로 정의 (지형 그리드, 타일 타입, 웨이브 테이블, 성벽 HP, 초기 코스트, 코스트 재생률).
- 입력도 데이터로: `{tick, action}` 시퀀스. 봇과 플레이어가 같은 입력 형식을 쓴다 → 봇의 플레이를 리플레이로 재생 가능 (디버깅·시연에 유용).

## client/ 규칙
- core의 상태를 구독해 렌더링. 게임 룰 로직 작성 금지 (룰이 필요하면 core에 추가하고 호출).
- Vite 빌드 → GitHub Pages 배포. GitHub Actions로 push 시 자동 배포 설정.

## bots/ 규칙
- 봇 = `(관측 가능한 state) -> action` 정책 함수. core를 헤드리스 루프로 구동.
- 최소 3등급: Greedy(단순 휴리스틱) / Planner(경로·DPS 계산 기반) / Random(하한 측정용).
- 등급별 성과 차이 자체가 난이도 신호다 (예: Planner는 깨지만 Greedy는 못 깨는 스테이지 = 상급).
- 오펜스 모드 구현 시, 디펜스 검증 봇의 정책이 곧 오펜스 자동 전투의 기반이 된다.

## pipeline/ 규칙
- 단계: 생성(LLM/절차) → 스키마 검증 → 봇 시뮬 N회 → 지표 산출 → 판정(출고/반려+사유) → 통과분 JSON 커밋.
- 모든 판정 결과를 `pipeline/reports/`에 기록 (반려 사유 포함). 이 리포트가 AI 활용 기술 문서의 증거 자료.
- 유료 API 호출은 파이프라인(빌드 타임)에서만. 런타임 빌드에는 생성된 JSON만 포함.

## 기술 선택 근거 (문서화용)
- 웹 스택: 심사자 접근 마찰 0(링크 클릭), 1인 개발 생산성, 48시간 본선 재현성, 참가자 역량이 웹.
- Phaser 3: 2D 그리드 TD에 충분, TS 지원, 번들 가벼움.
- 엔진 없는 Canvas 직접 구현 대비: 렌더링 잡무(카메라, 애니메이션, 입력)를 위임해 core 개발에 집중.
