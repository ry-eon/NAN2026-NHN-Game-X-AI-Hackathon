## 결정 사항
- **틱 레이트 30/s 고정**, 모든 시간 수치는 틱으로 환산 저장. 코스트는 float 누적
  (IEEE754 연산은 결정론적이므로 재현성 문제 없음).
- **근접 유닛은 ground + road 양쪽에 배치 가능** [초안 해석]: 기획서의 타일 분류에는
  진입로 배치 가능 여부가 명시돼 있지 않으나, 블로킹이 성립하려면 진입로 위 배치가 필수.
  명일방주 관례를 따라 근접=지상·진입로, 원거리=성벽 위로 확정.
- **블로킹 판정 = 셀 중심 반타일 이내 + 저지 여유 있는 유닛** (스냅 시 최대 0.45타일 전진 보정).
  저지 여유가 없으면 그대로 통과 — "초과 통과"가 난이도의 핵심 변수.
- **입력·이벤트도 데이터**: `{tick, action}` 시퀀스가 리플레이 형식이고, `state.events`가
  틱별 이벤트 로그. 봇 검증 리포트와 클라이언트 연출이 같은 이벤트를 소비한다.
- **step은 state를 제자리 변경**: 봇이 스테이지당 수천 틱 × N회 시뮬해야 하므로 할당 최소화.
- 스탯 수치는 전부 [초안]. 기준 스크립트(블로커→아처→브루저 3배치)로 stage-001을
  49.3초에 성벽 무손상 클리어 — 첫 스테이지 난이도로 적정, W2 난이도 지표 논의 때 재조정.
- RNG(mulberry32)는 W1 전투에선 미사용이지만 상태(number 1개)를 GameState에 넣어
  스냅샷 직렬화만으로 재현 가능한 구조를 선점.

## 추가 세션 (같은 날): client 최소 렌더러
- 지시: "client 렌더러 이어서 해줘"
- 결과: 채택. BattleScene 1개로 stage-001이 브라우저에서 플레이 가능.
  사각형(유닛)+원(적)+텍스트(HUD)만 사용 — W1 "아트 없이 플레이 가능" 기준 충족.
- **룰 로직 0 유지**: 배치 유효성 판단은 전부 core. client는 클릭을 `{tick, action}`으로
  큐잉하고 core의 deployRejected 이벤트를 토스트로 표시할 뿐. 배치 가능 타일 하이라이트도
  UnitDef.placement 데이터 표시이지 판정이 아님.
- **고정 틱 구동**: Phaser update에서 누적기(accumulator)로 core.step()을 33.3ms당 1회.
  프레임 드랍 시 틱 폭주 방지 상한(6틱/프레임).
- core 변경은 `enemyWorldPos` export 1건 (렌더러·봇이 적 보간 위치를 얻는 유일한 통로).
- 검증: 헤드리스 Chrome(playwright-core, 리포 외부 임시 설치)으로 스크린샷 3장 —
  초기 화면 / 블로커 배치 직후 / 웨이브 1 진행(t=9.3s, 적 3 전진). 콘솔 에러는 favicon 404뿐.
  헤드리스 특유의 RAF 스로틀링으로 초반 틱이 늦게 시작되는 현상은 실브라우저와 무관 판단.
